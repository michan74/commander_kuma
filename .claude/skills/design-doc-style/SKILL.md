# 設計書の書き方

設計書は「読む人が短時間で全体像を掴める」ことを最優先にする。長い説明文ではなく、ネストした箇条書きで構造化する。

## 絵文字凡例(ドキュメント冒頭に必ず入れる)

タイトルの直後、本文の一番上に以下の凡例を必ず記載する:

```
✅️ 採用
🗑️ 却下
👍️ 良い点
🥕 悪い点
```

## 全体構成

1. タイトル: `# YYYYMMDD_タイトル`
2. 絵文字凡例(上記)
3. 経緯・課題: なぜこの検討が必要になったか(先行ドキュメントがあればリンク)
4. サブタスク: `[リポジトリ][サブタスク名]` 形式の番号リストで列挙する(バックエンド/フロントエンド/運用作業など、性質が異なるものは別サブタスクに分ける)
5. 設計: `##`/`###`/`####` でトピックごとに分割し、詳細を書く

## 文体

- 箇条書きベース。文章を長々と書かない。体言止め・短文で端的に書く
- ネストで詳細を掘り下げる(見出しを増やしすぎない)
- ルールに従わない箇所があっても、なぜ従わないかの言い訳・注記は書かない(例: 「絵文字を使わない理由」等の注記は不要。単に使わなければよい)
- 1つの箇条書きに複数のアクション(「Aを追加し、Bも追加する」等)を詰め込まない。アクションが2つ以上あるなら、親の箇条書き1行にまとめず、ネストした子の箇条書きに分ける

## 検討事項の書き方

複数の選択肢で迷った場合:

1. 番号付きリストで選択肢を列挙する
2. 採用した選択肢の**先頭に✅️**を付ける。却下した選択肢には**🗑️**を付ける
3. 各選択肢の下に理由を箇条書きする。良い点・メリットには**👍️**、悪い点・デメリットには**🥕**を付ける
4. 最終的な決定は行頭に `->` を付けて**太字**で明記する。決定文の後は2行空行を空けてから次のセクションに進む
5. 会話でのやり取りや技術検証を経て判明した内容は、最初は単純な決定として書いていたものであっても検討事項の形式に直す。書き換え方は「決定後に問題が判明した場合」を参照

例:

```
✅️ 採用
🗑️ 却下
👍️ 良い点
🥕 悪い点

1. ✅️ 短冊に切って五線を探す
  - 👍️ 細い短冊の中では、傾いた線もほぼ水平になる
  - 🥕 短冊の幅を決める必要がある

2. 🗑️ 画像全体を回して、横方向の黒の量が一番くっきりする角度を探す
  - 👍️ 短冊の幅を決めなくてよい
  - 🥕 紙の曲がりはわからない

-> **写真の質の判定にも使えるため、短冊にした。**


### 次のセクション
```

## 決定後に問題が判明した場合

決定を変える場合は、旧い記述を`~~取り消し線~~`で消してから新しい内容を書く。後から読んでも経緯の履歴が追えるようにする。

- **検討事項(✅️/🗑️の比較リスト)だった場合**: 旧い✅️の選択肢を`~~取り消し線~~`で打ち消し、印を✅️→🗑️に変える。新しい決定を✅️付きの選択肢として追加する
- **検討事項ではない単純な決定だった場合**: `~~旧い記述~~` の後に `YYYY/MM/DD 変更:` と新しい内容を続ける

変更理由は「文体」のルールに従う: 結論を先に書き、理由・根拠は箇条書きで短文・明確に書く(長い経緯の説明文にしない)。

例(検討事項だった場合):

```
1. ~~✅️~~ 🗑️ ~~画像全体を、段ごとの傾きの中央値で回す~~
  - 🥕 斜めから撮った写真では、段ごとに傾きが残る

2. ✅️ 2026-10-03: 段ごとに回す
  - 👍️ 段ごとに傾きが違っても水平にできる
```

例(単純な決定だった場合):

```
~~AIの入力は楽譜画像全体~~ 2026-10-03 変更: 段ごとの画像
- 理由: 段ごとに水平に回してから渡すため
```

## リンク・参考文献

- 根拠となる外部ドキュメント(公式ドキュメント、ライブラリのリポジトリ等)は該当箇所にインラインで貼る
- 実装後は「対応PR」としてPRリンクを追記し、設計と実装の対応関係を残す
- `TODO:` は、まだ設計として決まっていない・確認中の事項にのみ使う
- 決定済みで、あとは実施するだけの作業項目は `TODO:` として書かない。それは実装作業であり、サブタスク側で管理する
- リポジトリ内のファイルは、リポジトリのルートからのパスで書く

## 図

- シーケンス図・構成図・ワイヤーフレームなどは、画像やファイルをリポジトリの `docs/` に置き、パスで参照する

## 複数リポジトリにまたがる場合

- 対応するリソース・変更ごとに「リポジトリ: xxx」と対象リポジトリを明記する
